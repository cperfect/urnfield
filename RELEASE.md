# Release Process

## Overview

Releases use a two-stage GitHub Actions workflow:

1. **[02 Prepare Release](.github/workflows/02-prepare-release.yml)** — run on a non-main branch. Validates the codebase and generates `CHANGELOG.md` using [git-cliff](https://git-cliff.org) from the conventional commit history.
2. **[03 Release](.github/workflows/03-release.yml)** — run manually from `main` after the prepared branch is merged. Reads the version from `CHANGELOG.md`, creates an annotated tag, and publishes a GitHub release.

The changelog is generated by `cliff.toml` at the repo root. Commit messages must follow the [Conventional Commits](https://www.conventionalcommits.org) specification for them to appear correctly in the changelog.

## GitHub Configuration

The following must be configured in the repository before the release workflows will function correctly.

### Repository visibility

The repository must be **public**. The Go module proxy (`proxy.golang.org`) cannot fetch from private repositories, so a private repo will not be indexed or installable via `go get`.

### `release` environment

Workflow `03-release` is gated by a GitHub environment named `release`, which restricts execution to the `main` branch.

To set it up:

1. Go to **Settings → Environments → New environment**
2. Name it `release`
3. Under **Deployment branches and tags**, select **Selected branches and tags**
4. Add the rule: **Branch** `main`
5. Save

Without this environment, `03-release` can be triggered from any branch.

## Cutting a Release

### 1. Create a release branch

```bash
git checkout main && git pull
git checkout -b release/vX.Y.Z
git push -u origin release/vX.Y.Z
```

### 2. Run the Prepare Release workflow

In GitHub: **Actions → 02 Prepare Release → Run workflow**, select the `release/vX.Y.Z` branch, enter the version (e.g. `v0.1.0`).

The workflow will:
- Validate the version format and confirm the tag does not already exist
- Run the full validation suite (format, vet, staticcheck, build, test)
- Generate `CHANGELOG.md` and commit it to the branch

If the workflow fails on validation, fix the issues on the branch and re-run.

### 3. Review and merge

Open a pull request from `release/vX.Y.Z` into `main`. Review the generated `CHANGELOG.md` — if the entries look wrong, check that commits on the branch follow the Conventional Commits format. Edit `CHANGELOG.md` directly on the branch if any manual corrections are needed.

Merge the PR once satisfied.

### 4. Run the Release workflow

In GitHub: **Actions → 03 Release → Run workflow**, select `main`.

The workflow will:
- Read the version from the top of `CHANGELOG.md`
- Create and push an annotated tag
- Publish a GitHub release with the notes for that version

### 5. Post-release: remove the examples replace directive

The prepare workflow updates the `require` version in `examples/ietf/go.mod` but keeps the `replace` directive (the tag doesn't exist yet when it runs). Once the release tag is live and the module proxy has picked it up, remove the `replace` directive and tidy:

```bash
# in examples/ietf/go.mod, remove the line:
replace github.com/cperfect/urnfield => ../..

cd examples/ietf && go mod tidy
```

Commit directly to `main`.

To confirm the module is available via the proxy before doing this:

```bash
GOPROXY=https://proxy.golang.org go get github.com/cperfect/urnfield@vX.Y.Z
```

If the proxy hasn't indexed it yet, visiting `https://pkg.go.dev/github.com/cperfect/urnfield@vX.Y.Z` will trigger indexing.
