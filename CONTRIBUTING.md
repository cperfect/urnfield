# Contributing
> This guide applies equally to both AI agents and meatsacks, unless otherwise stated.

## Use of AI
This project has been set up to use Claude code. 

Feel free to use whatever you want but please do not add artefacts for a different AI to your PRs.

Commits generated by AI (inc. Claude) should include the ai/model/version as co-author. 

## Git Workflow

This repository uses Trunk-Based Development using the default branch `main`. Changes should be divided into consistent working sets (e.g. a complete feature, fix, chore or related set of fixes, chores) on a branch based off `main` and a PR raised.

## Spec-First Development

`urnfield` is the Go **reference implementation** of the technology-agnostic
[`urnfield` specification](https://github.com/cperfect/urnfield-spec). The spec —
and its language-neutral **conformance suite** — is the single source of truth for
*behaviour*. It is vendored here as a git submodule under
[`submodules/urnfield-spec`](./submodules/urnfield-spec), pinned to a spec
version tag, and exercised by the conformance runner in `conformance_test.go`.

What this means in practice:

- **Behaviour-changing work is spec-first.** Anything that changes how URNs
  parse, format, validate, or compare — i.e. anything that would alter a
  conformance vector — must land in the spec repo **first**: update
  `SPECIFICATION.md`, add/adjust the conformance vectors, and cut a spec version.
  Only then update this repo to the new submodule tag and make the code pass. Do
  not silently diverge from the pinned spec; the conformance suite must stay
  green against the tag it points at.
- **Non-behavioural work stays local.** Refactors, performance work,
  documentation, new examples, test additions, tooling, and bug fixes that bring
  the code *into* line with the already-pinned spec need no spec change and can be
  done with an ordinary PR here.
- **Bumping the spec.** Updating the submodule to a new tag is itself a reviewable
  change: it should come with whatever code changes are needed to keep the
  conformance suite passing, and a CHANGELOG entry.

If you are unsure whether a change is behavioural, ask: *would any
`conformance/*.yaml` vector have to change?* If yes, it's spec-first.

## Code Style

Please follow the [go style guide](https://google.github.io/styleguide/go/), including the [best practices](https://google.github.io/styleguide/go/best-practices).

## Comments

GoDoc Comments should be provided for exported module members. 

Additional inline comments should be added for clarity when needed: e.g. for a complex algorithm, or if something non-obvious or unconventional/non-idiomatic choices have been made. Such comments should include *why* the choice was made.

## Commit Messages

Please follow [conventional commits](https://www.conventionalcommits.org/en/v1.0.0/)

## Testing

Please update the tests to reflect your code changes. Pull requests will not be accepted if they are failing on GitHub actions.

The conformance runner (`conformance_test.go`) drives the public API against the
spec's vectors and runs as part of `go test ./...`. It reads fixtures from the
`submodules/urnfield-spec` submodule, so make sure submodules are initialised (see
[Developing](#developing)) or those tests will fail to find their fixtures.

## Developing

Requires Go 1.26 or later. A dev container configuration is provided for VS Code and compatible editors — this is the recommended way to get a consistent environment.

This repo uses a git submodule for the specification and its conformance vectors.
After cloning, initialise it (clone with `--recurse-submodules` to do this in one
step):

```bash
# Fetch the urnfield-spec submodule under submodules/
git submodule update --init --recursive
```

```bash
# Install dependencies
go mod tidy

# Run the full test suite
go test ./...

# Check formatting (should produce no output)
gofmt -l .

# Run static analysis
go vet ./...
```

### Claude Skills

Two Claude Code skills are available to assist with code quality:

- **`/review-code`** — Reviews the codebase against the guidelines in this file. On `main` it reviews all Go source files; on a feature branch it reviews the diff against `main`; pass a PR number to review a specific PR. Runs `gofmt`, `go vet`, and `staticcheck` as part of the review. Optionally writes findings to a `code-review-findings_<timestamp>.md` file (gitignored).

- **`/fix-review`** — Works through a code review findings file issue by issue. Presents each finding, recommends a fix, and waits for your instruction before making any changes. Applies fixes with appropriate tests and comments, updates the findings file, and offers a commit after each resolution. Defaults to the most recent findings file, or pass a path explicitly.

## Running Examples

Examples are provided as runnable test packages under `examples/`. Each example demonstrates a real-world schema implementation.

```bash
# Run all examples
go test ./examples/...

# Run a specific example
go test ./examples/ietf
```
